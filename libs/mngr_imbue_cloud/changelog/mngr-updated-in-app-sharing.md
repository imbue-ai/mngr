The recipient's side of sharing (`specs/shared-with-me/spec.md`): `mngr imbue_cloud shares shared-with-me` lists every active share whose grants name the account (by account id, verified email, or the owner's own email domain), with the owner, the workspace name, each target's link and `is_granted_as_app` (whether a grant names the app itself beside a whole-workspace grant), the account's status (`invited`, `accepted`, `declined`), and the match set the listing was built from (each share's key, listing version, and the account's own standing), which `shares shared-with-me-matches` answers alone and the records listing carries as `shared_with_me_matches`, so a client refetches the listing only when the set changed. `shares respond <host_id> --response accepted|declined|reported` and `shares clear-response <host_id>` record and clear the account's response (a report is a strike against the owner and cannot be withdrawn); against a connector that does not serve the listing yet, all four fail with the code `shared_with_me_unavailable`. `mngr imbue_cloud auth browser-session-code` mints the single-use code of the reverse device handoff, which the desktop's embedded browser redeems for a session on the accounts origin. The connector now records the optional `targets` and `workspace_name` keys of the document `shares push-grants` forwards, which is where a recipient's links and names come from, and refuses a document that adds a domain grant its rules forbid with the code `grants_refused`, whose error body carries `refusals` naming each entry (`ImbueCloudShareRefusedError.refusals`). New wire models: `SharedWithMeListing`, `SharedWithMeShare`, `SharedWithMeTarget`, `ShareStatus`, `ShareGrantedVia`, `ShareResponseKind`, `ShareResponseResult`, `SharedWithMeMatch`, `SharedWithMeMatches`, `BrowserSessionCode`.
