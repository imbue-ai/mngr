The `imbue-studio` skill now tells an agent how to create a workspace where and as large as it should be: `launch_mode`, the connection (`cloud_account`), `instance_type` and the root `disk_gb` for the cloud modes, read off the agent's own entry in `GET /api/v1/workspaces` unless the user asks for a different machine, and `enable_web_access` only when the agent's own workspace is published and the new one is for the user's own use. Following the old text created a cloud workspace at the connection's default size with a 30 GB root disk.

`GET /api/v1/workspaces` reports each workspace's placement and size: `launch_mode` (stamped as a label at create, else read off the provider instance the workspace runs on), `instance_type` (stamped at create, so null on older workspaces) and the host's `cpu_count`, `memory_gb` and `disk_gb` as its provider recorded them. Under gVisor the sandbox hides the CPU model and the cloud metadata service, so an agent could not read its own instance type before.

New `GET /api/v1/workspaces/cloud-accounts` lists the cloud connections a create may target (name, alias, backend, pinned region, masked key hint, owning account; never a credential). It rides the `minds-workspaces-read` grant, like the rest of the workspace metadata. The create request's `disk_gb` description now says it is the VM's root disk for the cloud modes.
