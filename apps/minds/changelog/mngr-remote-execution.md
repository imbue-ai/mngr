- Agents in an approved workspace can now run commands on the user's computer, as the user, through `POST /api/v1/remote-execution/<device_id>`, behind three gates that must all be open: a new install-keyed setting (Settings > This computer, "Allow agents to run commands on this computer", off by default, stored on this device alone and never synced), a per-workspace latchkey grant of a new `remote-execution` request type pinned to the one device that approved it, and a re-check of the setting on every call, so turning it off stops every workspace at once. Turning the setting on opens a large warning that has to be acknowledged before it writes; the request popup's dialog carries the same warning, offers no Approve while the setting is off, and warns when the asking workspace is shared. The route takes an argv list, streams the command's output as NDJSON in the owner-exec `/run` shape (stdout and stderr lines, keepalives, one final exit line, no output cap), kills the command on timeout, on a dropped connection, or at shutdown, refuses the browser session cookie, and records every command's start and end under `events/remote_execution/events.jsonl` (never its output). The workspace Permissions tab gains a revoke-only "This computer" entry listing every device the workspace's agents may run commands on.

- The gateway's `permission-requests` extension accepts the new `remote-execution` type; its grant is never part of the services catalog, the cross-workspace verb file, or the agent baseline, so no other dialog's "all" or "any" switch can carry it (pinned by tests and a new `remote-execution` behavior corpus).
