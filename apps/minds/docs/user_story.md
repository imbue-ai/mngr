This is the primary flow for how a user would create a workspace for the first time:

1. User starts the desktop client. The loading screen plays the intro on the install's first launch (the lockup, two typed lines, the lockup parking in the titlebar) while the backend comes up.
2. Once the backend is ready and the install has never been taken past onboarding, the app lands on the sign-in page: "Reimagine your personal computer" over a Sign in button, with a "Help improve Studio" checkbox (checked to start; hovering over it shows what error reports carry and how long they are kept) and a "Use without an account" link at its foot. Pressing Sign in or the link saves the checkbox as the error-reporting setting.
3. Sign in opens the sign-in in the system browser, where the user signs in to an Imbue account or creates one. An account whose email is not verified yet is kept on the browser's check-inbox page until the emailed link is clicked: an account is signed in to the app only once its email is verified, so the app itself never waits on a verification.
4. When the sign-in lands, an account that already has workspaces goes to its home page, which lists them. An account with none gets its first workspace at once, on Imbue Cloud, with no further question. "Use without an account" opens the full create form instead (name, compute, backups, region, repository, branch), as a modal, on running the workspace on this computer.
5. Submitting a create lands on the creation page: "Welcome, \<first name\>!" over "Just a sec, we're setting up your workspace", a thin progress bar, the remaining time once more than a minute is left, and "Show details" over the create log. The desktop client clones the repository (if a URL) and runs `mngr create system-services@<host> --new-host --no-connect --label workspace_display_name=<name> --label is_primary=true --template main --template <mode>` (the agent id is read back from the `created` JSONL event rather than pre-generated). A create that fails says why on the same page and offers Retry, "Run on this computer", and Dismiss.
6. When creation completes, the workspace loads under a cover that carries the welcome on; once the workspace has its first page on screen, "Your workspace is ready!" stands for a beat and the cover fades into the workspace's provider page, where the user connects an AI provider or skips; the workspace's color then washes over the window, and the desktop opens with the main chat on the workspace's first conversation: the agent says who it is and what Studio is for, asks "How do you want to start?", and offers the ways to start as suggestions above the composer (`specs/chat-suggestions/spec.md`). A provider connected on the provider page has already started the workspace's first agent, so the user's first pick or message goes to it. The workspace's own tour waits for that first conversation to end, then starts beside the agent's avatar the moment an agent goes to work (and pauses when the agent answers, to resume on the next task).

For subsequent launches:
- The loading screen opens on the parked mark and status line; no intro plays.
- If the user has workspaces (or has completed onboarding), they land on the home page listing every workspace, or on their restored windows.

Creating additional workspaces:
- Users press Create on the home page, fill in the form, and land on the same creation page, headed "Setting up \<workspace name\>".
- Programmatic creation is available via `POST /api/v1/workspaces`, polling `GET /api/v1/workspaces/operations/create/{operation_id}` for progress.

The point of this whole flow is to make it as easy as possible for users to get a workspace running.
